## 1. The test precondition — fixed, and it was the pattern, not the test

You asked me to decide where the fix belongs. **It belongs in the suite**, and
finding a fourth instance while fixing the third settled it.

`tests/test_waf_crs_tree.php` asserts what happens when no other ModSecurity
ruleset exists. The container seeds one at the cPanel vendor path defining
`900990`, exactly as a real cPanel server does, so the scanner correctly found
a collision and the assertion failed against **correct behaviour**.

Fixing that surfaced a **fourth**: `tests/test_waf_restore_verified.php:412`
asserts the message contains `could not identify` — the wording that only
appears when there is no other ruleset to identify. With the seeded vendor
ruleset present the explanation correctly takes its other form, names the
ruleset it found, and that assertion failed too.

So: `scan_types`, `waf_categories_real`, `waf_crs_tree`, `waf_restore_verified`.
Four tests, one cause — **product code reading hardcoded absolute paths with no
injection point**, which leaves a test no way to describe the world it needs.
Where an override exists the problem evaporates: `setConfDir()`,
`setIncludeDir()`, and `setCrsPath()` (added for N3) are exactly that, and the
tests using them need nothing special.

**What I added:** `tests/env.php`, with `t_env_without_foreign_rulesets()`. A
test declares the environment it requires; the helper makes it true by moving
the matching files aside, **prints what it moved**, and restores them on
shutdown including after a fatal. Each test file runs in its own process, so
the blast radius is one file. I verified the vendor ruleset is back in place
after a full run.

It prints because a test that quietly rearranges the machine and then passes is
worse than one that fails honestly — the next reader has to be able to see the
pass was conditional, and on what.

**It is a workaround and the file says so.** The durable fix is an injectable
override on `WAFInstaller::FOREIGN_RULE_GLOBS`, the same shape as `setCrsPath()`.
That is a product change and it is yours, not mine.

## 4. Finding 13's grace ladder — now genuinely executable

I flagged last round that I had established this by reading the call graph, not
by running it. `buildLocalKey()`'s optional timestamp closes that honestly —
production passes nothing, and the signature still binds the date, so nothing is
weakened. Run one process per case (`status()` memoises, so a single process

```
today                 valid=true  degraded=false Active   License active.
10d old               valid=true  degraded=false Active   License active.
20d old (in grace)    valid=true  degraded=true  Active   License server unreachable. Operating on cached license for …
400d old (past grace) valid=false degraded=true  Unknown  License server unreachable beyond the grace period. …
```

`LOCALKEY_DAYS = 15`, `GRACE_DAYS = 10`. The ladder behaves exactly as
described: a blip keeps protection on and says so, and past grace it gates
rather than pretending. **The gap I flagged is properly closed.**

### Minor — a future-dated key never expires

You asked me to satisfy myself the window cannot be extended indefinitely. It
can:

```
FUTURE +1y            valid=true  degraded=false Active   License active.
FUTURE +10y           valid=true  degraded=false Active   License active.
```

`$age = (time() - checkdate) / 86400` goes negative for a future date, so
`$age < LOCALKEY_DAYS` is true forever: the key is treated as freshly verified,
never becomes degraded, and the product silently stops re-verifying.

**Not an outsider-exploitable hole.** `localSalt()` is `random_bytes(32)` stored
in the database, under a 0700 root-owned directory — forging a key means
already having root. The realistic causes are a server clock set ahead, or a
clock corrected backwards after a key was issued. It fails *open* (keeps
protecting), so no customer is harmed; it is a licensing and
stopped-checking issue.

**Expected:** clamp the age at zero, or treat a checkdate in the future as not
verified. One line either way.

*(Aside: `(int)$decoded['checkdate']` at `License.php:341` looks wrong, because
`checkdate` is written as `date('Ymd')`. It is fine — `decodeLocalKey()`
converts it with `strtotime()` before returning. I checked because an `Ymd`
string cast to int would have made every key look 20,000 days old.)*
