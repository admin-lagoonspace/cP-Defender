### Minor — a future-dated key never expires

You asked me to satisfy myself the window cannot be extended indefinitely. It
can:

```
FUTURE +1y            valid=true  degraded=false Active   License active.
FUTURE +10y           valid=true  degraded=false Active   License active.
```

`$age = (time() - checkdate) / 86400` goes negative for a future date, so
`$age < LOCALKEY_DAYS` is true forever: the key is treated as freshly verified,
never becomes degraded, and the product silently stops re-verifying.

**Not an outsider-exploitable hole.** `localSalt()` is `random_bytes(32)` stored
in the database, under a 0700 root-owned directory — forging a key means
already having root. The realistic causes are a server clock set ahead, or a
clock corrected backwards after a key was issued. It fails *open* (keeps
protecting), so no customer is harmed; it is a licensing and
stopped-checking issue.

**Expected:** clamp the age at zero, or treat a checkdate in the future as not
verified. One line either way.

*(Aside: `(int)$decoded['checkdate']` at `License.php:341` looks wrong, because
`checkdate` is written as `date('Ymd')`. It is fine — `decodeLocalKey()`
converts it with `strtotime()` before returning. I checked because an `Ymd`
string cast to int would have made every key look 20,000 days old.)*

## Wasooli — the 10 Nov customer-scan incident (fixed here, for Shakaal to test)

Not from this report: the live fault diagnosed on the server this afternoon.
Three commits, `72748a6`, `b404d1f`, `28578bd`, and this is what to attack.

**One inherited file descriptor.** `UserScanRequest::lock()` keeps its flock
handle open deliberately; `Scanner::startScan()` then spawns the worker through
the shell, and the child inherited the descriptor and the lock. The pickup
exited, the lock did not. `fuser` on the server showed it held by `clamscan`,
with the pickup PID long dead — so the lock's lifetime had become the scan's
lifetime, and with a nightly sweep running 2 days 11 hours, every customer
scan request on 132 accounts was refused from Sunday.

The descriptors are closed in the child by the shell (`N>&-`), because PHP has
no portable close-on-exec for streams at 7.4 and 8.5 and the shell is on both
ends of every spawn here. **Demonstrated in the container, with a control:** a
child spawned the new way holds no descriptor on the lock file and a second
pickup can take the lock while that child runs; the same child spawned without
the close-list inherits it. The control is the part that makes the first
assertion mean anything.

Please attack:

- **the close-list against a real `scan.php`**, not my `php -r` sleeper — the
  real chain was php → sh → timeout → clamscan, and `timeout` is the one I
  have not watched;
- **`--watch` mode across passes**, now that the lock is released at the end
  of each pass rather than at process exit;
- **the diagnosis text on a server where /proc exists but the holder is a
  sibling**, not a descendant.

**The silence was the second fault, and the reason it took three days.** A
refused pickup returned with no log, exit 0, and skipped the timestamp that
would have shown it. There are two timestamps now — attempt (always, before
the lock) and run (only with the lock) — and a fresh attempt beside a stale run
is the signature. `--status` prints both and says "PICKUPS ARE BEING REFUSED
since …" with the remedy; the log line is first-then-every-ten-minutes, carries
the number of waiting customers, and names the holder.

**The third was what the customer saw.** "Queued", in green, for two and a half
days. It now reads "Not started" in amber after five minutes, decided from the
age of the request file in their own home — the one signal on that page that
does not depend on report.json, the database, or the pickup working.

### Asked for an opinion, not a patch: the 2-day nightly scan

**It is a missing bound, not a scan that is too broad, and not expected.**

The job in the incident was `--path=/home/aaksh/public_html,…` across ~120
accounts: that is the *quick* resolution — web roots only — already the
narrower of the two. Narrowing further would mean not scanning customer web
content, which is the one thing this product exists to scan. So the scope is
right and the control over it is missing:

1. **There is no wall-clock budget on a job.** `scan_batch_timeout` (600s)
   bounds a single clamscan invocation; nothing bounds the *job*. A sweep that
   does not fit its window therefore does not fail — it becomes permanent,
   overlaps the next night, and the night after. That is the actual defect, and
   it is the same shape as every other finding this week: the product does not
   know a thing and does not say so, in this case "I did not finish".
2. **It then blocks customers for a second, independent reason.**
   `scan_max_concurrent` is 1, and `startScan()`'s third argument is
   `ignoreBackup`, not ignore-concurrency — so a permanent nightly sweep
   refuses customer scans even with the lock fixed. Whatever is done about the
   budget, **a customer sitting in front of a page is a different priority from
   a background sweep**, and I would give user scans a reserved slot rather
   than let them queue behind a job with no end.
3. **Measure before choosing the fix.** 1,339 files in 4s in the container
   against 2.5 days on the real box is not a files-per-second story; it points
   at per-batch clamscan startup, which loads the whole signature database
   (most of a gigabyte) every time. If that is confirmed, the lever is batch
   size or a resident `clamd`, and a time budget alone would just produce a
   sweep that never reaches the last accounts. If it is not confirmed, the
   budget plus a deterministic rotation (a slice of accounts per night, every
   account covered within k nights) is the honest bound.

My recommendation: measure the per-batch cost first, then budget + rotation,
with the reserved slot for customer scans regardless. All three are bigger than
this patch and I have not touched them.
