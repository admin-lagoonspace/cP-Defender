## The correction — you were right and I was wrong

I reported that `file_put_contents()` returns a short count rather than `false`.
**That is incorrect.** Settled in the container, on a 64 KB tmpfs, both versions:

```
                           PHP 7.4.33          PHP 8.2.35
file_put_contents return : false (boolean)     false (boolean)
  warning                : "Only 65536 of 200000 bytes written,
                            possibly out of free disk space"
fwrite return            : 65536 (integer)     65536 (integer)
```

`file_put_contents()` returns **`false`** on ENOSPC with a suppressed warning.
The short count is `fwrite()`'s. Wasooli is right, I was wrong, and the
sentence in my 2026-11-09 report should not be relied on.

**The conclusion it was supporting still holds, for a different reason.** Look
at the third line: 65,536 bytes *were* written. The call returns `false` **and
leaves a truncated file on disk** — so a caller that checks `=== false` and
stops has still replaced a good config with half a config. The byte-readback
check is what actually earns its place, not the short-count branch I argued for.
`writeAll()` now does an `fwrite` loop and returns real bytes written, which is
the correct shape regardless of which of us was right about the wrapper.

I have corrected the claim in the 2026-11-09 file rather than leaving it to
propagate.

## 1. The N4 collision message, from a real colliding server

Built the configuration rather than a fixture: the distro `mod_security_crs`
3.3.4 at `/etc/httpd/modsecurity.d/` (loaded by `mod_security.conf`'s
`IncludeOptional modsecurity.d/*.conf`) alongside our CRS 4.7.0. Both define
`id:900990`. Real Apache rejected it. **The sentence the operator gets:**

> Apache rejected the change. ANOTHER MODSECURITY RULESET ON THIS SERVER
> DEFINES THE SAME RULE ID: 900990 (also defined in
> `/etc/httpd/modsecurity.d/crs-setup.conf`); 901001 (also defined in
> `/usr/share/mod_modsecurity_crs/rules/REQUEST-901-INITIALIZATION.conf`); …
> and 434 more. Each ruleset is valid on its own; Apache cannot load both,
> because a rule id has to be unique across the whole configuration. Disable
> one of them — on cPanel, the vendor ruleset is switched off in
> WHM > ModSecurity Vendors — and set the mode again. Nothing in
> `/etc/serverscrub/waf/coreruleset` defines an id twice., so it was rolled
> back: …

It names the real foreign file, resolves the symlinked `activated_rules` back
to `/usr/share/mod_modsecurity_crs/`, says both rulesets are valid alone, gives
the cPanel remedy by name, and explicitly clears our tree. Against the raw
`AH00526 … line 818 of /etc/serverscrub/waf/coreruleset/crs-setup.conf` that
Apache produces — which points at us — this is a large improvement, and it is
the sentence a real server produces, not a fixture.

**The off-list fallback, also built rather than mocked.** A ruleset at
`/opt/somebodys-rules/`, included from a hand-written httpd conf, nowhere in
`FOREIGN_RULE_GLOBS`. The scanner finds 0 collisions, and the wording is:

> Apache reports a duplicate rule id, and the tree at
> `/etc/serverscrub/waf/coreruleset` **defines each of its own ids exactly
> once**, so the second definition is in a **ruleset this check could not
> identify**. It looked in: [the seven globs, listed]. A second OWASP CRS
> loaded by Apache is the usual cause (cPanel ships a vendor ruleset);
> `apachectl -t` names the file it was reading when it stopped.

That is exactly the right answer: it states what it established, does not blame
our tree, names where it looked, and points at the next step.

**One blemish, minor:** `…defines an id twice., so it was rolled back:`. The
explanation ends in a full stop and `', so it was rolled back'` is appended
after it. A stray `.,` in the middle of the sentence an operator reads at 3am.

> I twice reported this message as missing because my own harness split the
> error on `|` and printed only the tail. Both times the product was right and
> my tool was wrong. `waf-live.sh` now prints the whole string, newlines folded.

## 5. Finding 13 — a transient licence failure is not treated as a definitive no

`noteRemoteNegative()` is reachable only from inside

```php
if ($results['status'] === 'Active') { … } else { … noteRemoteNegative(...) }
```

— i.e. only where the server answered and its status was parsed. A transport
failure returns before that and goes through `noteRemoteFailure()`, and the
caller falls through to the cached licence:

```php
$remote = self::remoteCheck($key);
if ($remote !== null) { return $remote; }
if ($age < (self::LOCALKEY_DAYS + self::GRACE_DAYS)) {
    return self::fromResults($decoded['results'], true,
        "License server unreachable. Operating on cached license for {$left} more day(s).");
}
```

`GRACE_DAYS = 10`. So a network blip keeps a valid licence working, flags
`degraded`, says so in words, and re-asks after `REMOTE_RETRY_SECS = 900`. The
back-off suppresses *asking*, never the verdict. The failure mode you were
worried about is not present.

**Stated honestly:** this one I established by reading the code and the call
graph, not by executing it. My attempt to drive it ran on a Trial licence,
which never contacts the server at all, and forging a stale signed local key to
reach the grace branch was not something I could do safely. The two branches are
unambiguous in source; they have not been watched.
