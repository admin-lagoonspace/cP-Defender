## THE CAVEATS, in one place

1. **`cache` and `.cache` are invisible to every scan type, at every depth,
   including a full scan.** Disclosed now, not closed. Malware was found in
   `/home/officialwebspace/.cache/` on this server, re-executed every minute
   from a user crontab. The operator is now told; the scanner still does not
   look. This is the biggest known hole in the product and it ships open.
2. **Finding 5, the mass-detection card in the panel, is not built.** I accept
   deferring it (reasoning below) on the condition it is specced rather than
   remembered.
3. **The CSF geo-block write is verified against a stub `csf` binary at the
   real paths, not against a real CSF install.** The file handling is real; the
   firewall's own response to `csf -r` is not exercised.
4. **One branch of the geo-block write could not be executed at all** — the
   failed/short write. Asserted structurally, labelled as such, reasoning below.
5. **Untested surface, carried forward unchanged:** cpsrvd, WHM AppConfig,
   LiveAPI and the CGI wrappers (installed `--mode standalone`); real
   ModSecurity under Apache; real Exim (`exim -bp` stubbed); real ClamAV
   (stubbed, EICAR only); scale (8 accounts, 1,645 files — not 132 accounts,
   not 154,323 findings on disk); `quarantine restore` against a real 204 MB /
   154,323-row quarantine (five hand-built rows).
6. **Two new minor findings** below, neither in scope tonight: a false sentence
   in the restore refusal message, and `MailQueue.php:463`.

## The item you least wanted to take on trust: the CSF destructive path

I attacked this two independent ways and they agree.

**Route 1 — no seam at all.** `tests/tools/csf-geoblock-probe.php` creates a
real `/etc/csf/csf.conf` at the real path and a real executable at
`/usr/sbin/csf`, then drives `setGeoBlock()`/`getGeoBlock()` with
`setCsfPaths()` never called, and asserts on **the bytes on disk** after each
call. **27 assertions, 0 failures.** It covers: the rewrite actually changing
`CC_DENY` (normalised, deduplicated, upper-cased, read back from the file); the
rest of `csf.conf` surviving; the empty-selection refusal leaving `CC_DENY`
**byte-for-byte unchanged**; `clear_all` genuinely emptying it; a missing
`CC_DENY` directive as a failure; a non-zero `csf` exit reported as "would not
reload" with `enforced: false` *and* honestly reporting that the file was
written; a bad country code rejected before any read or write; and
`getGeoBlock()` returning `null` rather than `[]` for an unreadable conf.

**Route 2 — the seam.** `tests/test_geo_block_wipe.php`, **39 assertions, 0
failures**, and it does **not** touch the real `/etc/csf/csf.conf` (verified
with a sentinel value and `diff`), so its hygiene is right.

**Is the seam a lookalike?** No. Every call on the destructive path goes
through the accessors — `self::csfConf()` at the `file_get_contents` (674), the
`preg_replace` target, the `file_put_contents` (690) and all three error
strings, and `escapeshellarg(self::csfBin())` at the `exec` (699). There is
exactly one `file_put_contents` against the conf in the whole class and it is
that line, so the seam test and my seam-free probe execute **the same
statement**, differing only in the string it resolves to. `setCsfPaths(null)`
restores the constants, so production behaviour is unchanged.

**What I could not do:** make the write fail. The product runs as root and so
does the test; `chmod 0444` does not stop root (verified: `file_put_contents`
on a 0444 conf as root returns `int(1)`), `chattr +i` needs
CAP_LINUX_IMMUTABLE and e2fsprogs is not in the image ("chattr: command not
found"), and making the path a directory trips the earlier `cannot read`
branch instead. On a real server the trigger is ENOSPC, which surfaces as a
**short write rather than false** — so the half that matters is
`$wrote !== strlen($new)`, and that is asserted structurally and labelled in
the file as the only structural assertion in it. Caveat 4.

**Conclusion:** this is as strong as it gets without a real CSF install, and
the verification does not rest on a seam anyone has to trust. The branch that
has been wiping live firewall lists since `e2dcbd1` is now exercised for real.

## Rulings

### The 8-character wildcard — the boundary HOLDS. I was wrong about the floor.

Measured at `18d2ec2`: `--signature='*'` **REFUSED**, `--signature='{HEX}*'`
**REFUSED**, `{HEX}ph*` (7 before the `*`) **REFUSED**, `{HEX}php*` (8)
allowed, `--ext=md` alone **REFUSED**, `--ext=tar,gz,zip` alone **REFUSED**,
`--signature='*' + --job=` **REFUSED**. The hole I found is closed and the
floor is exactly where it is documented to be.

On the remaining case — a family wildcard as the sole scope — **Wasooli's
argument is better than mine and I withdraw my proposed higher floor.** I
argued the restore floor should exceed the suppression floor because restore
writes attacker code to disk while suppression only stops reporting. That
asymmetry does not hold up: a suppression that is too broad hides live malware
server-wide and indefinitely, which is how six and a half months went by on
this server. One shared floor that both paths raise together is more
defensible than two numbers drifting apart for reasons nobody will remember in
a year.

I also agree with its proposed change in preference to mine: **no number of
characters makes `*` safe**, so an extra explicit flag for `--apply` on a
wildcard-only scope is the right shape. That is a hardening, not a defect —
dry-run is the default and the dry run prints the signature, account and
extension breakdown before anything moves. **Recommended as a follow-up, not a
release blocker.**

### Finding 5, the WHM card — I accept shipping without it. The release does not stop here.

Spec requirement 7 asked that the bound stay operator-visible. What I wrote as
"Expected" in the `55bd3d5` report was "a `serverscrub scan mass-bound [N]` or
equivalent, listed in `--help`, plus the last trip alongside it". That is
precisely what was built, and I verified it against a real install:

```
  scan mass-bound [N]          Show or set how many files ONE signature may …
mass_signature_max:    500      →  2000
was:                   500
means:                 past 2000 files from one signature in one scan, findings are
                       flagged and left in place … The scan still runs to the end
high|Mass-detection bound changed from 500 to 2000 by the CLI
scan_mass_signature_max|2000
```

I asked for it and got it. The card would be a second surface for facts that
already reach the operator twice — the CLI and a critical `mass_detection`
security event in the Events panel — and `frontend/index.html` is Gabbar's file
on release day. Accepted, conditional on it being specced rather than carried
in someone's head.

### `builtinExclusions()` and spec line 118 — satisfied.

One line, as asked: **yes.** The list now names `node_modules`/vendor, the
bind-mount trees, and "Any directory named cache or .cache, at any depth —
INCLUDING inside an account home. Malware has been found in .cache on this kind
of server, so this is a known blind spot, not a safe assumption". Confirmed
rendering in the Scanner panel. Naming it as a blind spot rather than as a safe
exclusion is the part that makes it satisfy line 118, and it goes further than
the four bare entries I asked for.

### The `.cache` deferral — still stands.

One line, as asked: **yes, with the stopgap in place the deferral stands.** The
cost argument is sound and unchanged, the replacement bounds genuinely do not
exist, and a bare removal tonight would be the 59-hour scan again. But
disclosure is not coverage: the hole is now honest, not smaller. Caveat 1, and
the thing I would put at the top of the next cycle.

### Finding 2: the WAF card — FIXED, and verified in the rendered panel

The card at `18d2ec2`, on a server with an empty CRS directory:

```
WAF ENGINE        No rules loaded
ModSecurity is installed and a rule set directory exists (…/OWASP3) but it
holds NO RULE FILES, so nothing is being inspected, nothing is being logged
and nothing is being blocked. This is not protection.
ModSecurity       installed, version unknown
```

Every one of the three statements that used to contradict each other now

why both can be true.

## New findings (minor, not in scope tonight)

### A. The restore refusal message states something the product does not do — minor

`--ext=md` alone is refused with: *"A wildcard signature or an extension
narrows a restore; it cannot define one."* But a wildcard signature of 8+
characters **does** define one — `--signature={HEX}php.cmdshell.gifheader*`
alone is allowed, by design. The sentence is true of extensions and false of
wildcards. It is only ever shown to someone who used `--ext` (a wildcard makes
`$narrow >= 1`, so this branch cannot fire with one), and it misleads in the
direction of making the product sound stricter than it is. Reword to: *"An
extension narrows a restore; it cannot define one. A signature wildcard needs
at least 8 characters before the `*`."*

### B. `MailQueue.php:463` renders an exim failure as "0 messages queued" — minor

Noted so it is not lost, per your message. Confirmed:

```php
$o = (string) @shell_exec('nice -n 19 ' . escapeshellarg($bin) . ' -bpc 2>/dev/null');
return (int) trim($o);
```

Unchecked stdout cast to int, so any failure becomes `0`. A count rather than a
protection claim, which is why it is minor — but it is the same defect class as
the `rpm -q` one just fixed, and "0 messages queued" on a server whose queue is
backed up reads as healthy. Agreed it is out of scope tonight.
