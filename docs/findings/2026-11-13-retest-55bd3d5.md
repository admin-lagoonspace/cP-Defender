### 2. The declines

**Decline A — "a real mass detection should still be acted on (`act === true`)".
The decline HOLDS. I withdraw the assertion.**

Spec requirement 2 is explicit: "Past the bound, destructive action
(quarantine, disable, delete) stops for that signature… **This part of the
current behaviour is correct and must survive.**" The spec separates halting
(harmful) from flagging (the right conservative default) and keeps the second
deliberately. I was reading the brief's "must not leave files in place" as an
absolute when the spec had already resolved that tension on the other side.
Wasooli is right and I was wrong; the assertion is withdrawn from
`tests/findings/shakaal_mass_detection_open.php`.

**Decline B — "all-distinct must be `undetermined`, not `varied-content`".
PARTIALLY holds. I accept the verdict name and reject the advice attached to it.**

The decline's grounds are sound as far as they go. Requirement 3 explicitly
endorses "sampled content identicality" as evidence, so a content-based verdict
is permitted; requirement 4's bar is "on count **alone**", which this clears.
And on the two incidents that actually happened the verdict is right both times
— 30 Apr was identical, 10 Nov was all-distinct.

But requirement 4's *principle* — where it cannot tell, it says it does not
know — does bite here, because a ransom note that embeds anything per-file (a
counter, a victim id, the account name in the body) and a changelog false
positive are **equally consistent** with all-distinct hashes. Naming one of two
equally-supported hypotheses is a guess.

I am not pressing the verdict name, because the practical harm is not the word
— it is the command that comes with it. See the finding below, which also
covers the `undetermined` path and makes this one fix rather than two.

**Decline C — `CLUSTER_FLOOR = 50` adopted. Verified correct.**
`weigh(500, 251, 250)` → `top 250 >= 50` → `undetermined`. My mixed-job
assertion is satisfied.

**Decline D — "there is an undo and no do", real but out of scope.** Confirmed
real. It is not fully out of scope, though: see blocker 3.

## Findings

### 1. The Firewall page throws on every load, and "Save Geo Rules" silently removes every country block — blocker

Unchanged from the `386bca0` report and not addressed by this commit.

`renderGeoGrid()` (`frontend/js/app.js:1955`) reads
`Database?.setting?.('geo_block_countries')`. `Database` is a PHP class; it does
not exist in the browser, and `?.` does **not** guard an *undeclared*
identifier — it throws. So the country grid never renders, the exception escapes
`loadFirewallStages()`, and `State.geoSelected` is empty on every load.
**Save Geo Rules** then posts `[]`, `Firewall::setGeoBlock([])` rewrites
`CC_DENY = ""` and runs `csf -r`, and the operator gets a green
`Geo block saved (0 countries)`. `setGeoBlock()` returns `['success' => true]`
unconditionally — it checks neither the write nor `csf -r`.

One page visit plus one click removes a server's entire geographic block list
and reports success.

**Reproduce:** `docker compose -f docker/compose.yml up -d panel`, sign in,
click **Firewall**, then `read_console_messages`.

**Evidence:**
```
[error] page load failed: firewall ReferenceError: Database is not defined
    at renderGeoGrid (http://localhost:8777/js/app.js?v=4.35.1:1955:17)
    at loadFirewallStages (http://localhost:8777/js/app.js?v=4.35.1:1868:3)
```

### 2. The WAF card claims "ModSecurity is installed and logging matches" with no rule files, and prints a "not installed" message as the version — blocker

Unchanged from the `386bca0` report. The panel renders, simultaneously:

```
WAF ENGINE   Installed
ModSecurity is installed and logging matches, but not blocking them yet.
ModSecurity   installed package ea-apache24-mod_security2 is not installed
OWASP CRS     vunknown
… The OWASP CRS directory … holds no rule files that could be read.
```

- `WAFInstaller::modsecVersion()` ends with
  `shell_exec('rpm -q --qf "%{VERSION}" ea-apache24-mod_security2 2>/dev/null')`.
  rpm prints `package <name> is not installed` on **stdout** and exits 1;
  `2>/dev/null` redirects the wrong stream and the exit code is never checked,
  so that sentence is returned as the version.
- `crs_installed` is `crsPath() !== null`, which only tests that the directory
  exists. An empty CRS directory — the state `f1844fb` existed to clean up —
  reads as installed, so `ready` is true and the card asserts the engine is
  "logging matches" with nothing to match against.

This is the `MODE = 'On'` class: a protection claim with nothing behind it.
Partly shaped by the container (no real ModSecurity), but both defects are in
the logic, not the fixture.

### 3. Spec requirement 7 is not met: the bound is not operator-visible — blocker

Requirement 7: "`scan_mass_signature_max = 0` still disables the bound
entirely, and **the setting remains operator-visible**."

The row exists (`scan_mass_signature_max|500`, confirmed after a real install)
and `grep -rn scan_mass_signature_max backend/ frontend/ cpanel/ whm/` returns
exactly two hits: the default row in `Database.php:399` and the constant name
in `MassDetection.php:132`. **No CLI command, no Settings field, no help text,
no label anywhere.**

**Correcting my own earlier report:** I wrote that the only route was
hand-editing the settings table. That is wrong. `routeSettings` `get` returns
*every* settings row and `set` accepts any key matching `^[a-z_]+$`, which this
key does — so an authenticated admin can read and change it through the generic
API. It is reachable, but it is not *discoverable*: an operator cannot find it
from the product.

Why this is a blocker rather than a nice-to-have: it is the other half of
finding 4. Past the bound a real mass event leaves the remaining findings
flagged and in place by design, and the only ways forward are a suppression
(wrong — it hides a real infection), a per-file verdict at 153,800 files
(infeasible), or raising this bound. The spec required the lever to be visible
precisely so the chosen design has an exit, and it has not been built. Shipping
the flag-and-wait behaviour without it means the next real incident is handled
by someone guessing a settings key.

**Expected:** a `serverscrub scan mass-bound [N]` or equivalent, listed in
`--help`, plus the last trip (finding 5) alongside it.

### 4. Wasooli's "it never says suppress" claim is false — major

The named soft spot — a per-victim note spread thinly — was tested directly
(`tests/tools/suppress-claim-probe.php`, 600 samples, 118 distinct, top group
6). It does return `undetermined`, and the honesty of the verdict is genuinely
good: "THE PRODUCT CANNOT TELL whether these are one file repeated or many
different files, and does not guess", with the basis and sample size stated.

But the safety argument offered for shipping it does not hold. Precisely: the
**row reason** names suppression in prose only ("suppress the signature if it
is wrong") and carries no command — that part is fine. The **critical alarm**,
which is the thing an operator is paged with, hands over a ready-to-paste
command:

```
Read one of the flagged files, then either `serverscrub signatures suppress add
{HEX}linux.ransom.sessionscribe.qtox.toxid.171.UNOFFICIAL` if the signature is
wrong, or treat it as a real mass event and decide the scope of the clean-up.
```

```
CLAIM CHECK: text contains 'suppress'?                YES
CLAIM CHECK: text contains 'signatures suppress add'? YES
CLAIM CHECK: says do NOT suppress?                    no
```

That is a composed, copy-pasteable instruction for switching off detection of a
live ransomware run, shown at 03:00, in the one case the product has just said
it cannot judge. The text is even-handed and conditions the advice on reading a
file first, which is why this is major and not a blocker — but "it never says
suppress" is not what the code does.

**This is also my answer to decline B.** The fix for both: give the
pre-composed `signatures suppress add` line **only** for `varied-content`, and
for `undetermined` name suppression as an option without writing the command
out — exactly as the row reason already does. Where the product cannot tell, it
should not be pre-typing the dangerous branch. (Memory rule, same spirit: never
hand over a path you have not read.)

Encoded as an assertion in
`tests/findings/shakaal_mass_detection_open.php` (12 pass, 2 fail — the two
fails are this finding and blocker 3).

### 6. CORRECTION — a FULL scan is blind to `.cache/` and `cache/`, not just a quick scan — major

**I got this wrong in the `386bca0` report.** I wrote that the full scan "walks
those paths" and that only the quick scan was narrow. That is false for
`.cache`, which is where the live artefact sits.

`SCAN_SKIP_DIRS` (`Scanner.php:941`) contains `'cache', '.cache'`, matched
against `strtolower($current->getFilename())` at **every depth**, in both walks.
Measured with EICAR probes (the only thing the stubbed ClamAV flags, so the only
honest test of "was this read"), one per location, full scan of `/home`:

| probe location | found by a FULL scan |
|---|---|
| `public_html/` (control) | FOUND |
| `$HOME/` | FOUND |
| `.cache/` | **NOT SEEN** |
| `cache/` | **NOT SEEN** |
| `.cpanel/caches/config/` | FOUND |
| `tmp/webalizer/` | FOUND |
| `.cphorde/` | FOUND |
| `ssl/` | FOUND |

Note the inconsistency this exposes: `.cpanel/caches/` is scanned because the
directory is named `caches`, plural, which is not in the list. So the prune is
narrower and more arbitrary than it reads.

Quick-scan coverage separately: `Scanner::accountsForScan()` builds
`'docroot' => is_dir($home . '/public_html') ? $home . '/public_html' : null`
and **never reads `documentroot` from `/var/cpanel/userdata`**, although
`CMSGuard.php:137` does exactly that. Quick scan read 55 files of 1,645; full
scan read 1,345.

The code fact above is solid. **I could not pin the end-to-end consequence for
the `deepnest` account** and am not claiming it: the seeded layout differs
between container runs. In one run the quick scan's `scan_path` included
`/home/deepnest/public_html` (which exists but is empty, so the operator is
told deepnest was covered while the real docroot was never opened); in a fresh
container `/home/deepnest/public_html` did not exist at all and
`/home/deepnest/sites` held no files. Either way the custom `documentroot` is
not consulted, but `docker/seed-cpanel.sh`'s non-`public_html` docroot needs to
be made deterministic before this can be asserted as a measured result rather
than a code reading.

**On the deferral: I agree, with one condition.** A bare removal of `.cache`
tonight would be wrong — under an account home it holds npm/composer/pip trees
of the same order as `node_modules`, `/home/virtfs` makes `find` multiplicative,
and the replacement bounds do not exist yet. Deferring the prune change is the
right call and I would make the same one.

The condition is spec line 118: "A scan that skipped directories must not
report clean coverage." Nothing discloses the skip. The Scanner panel's
"Already excluded automatically" list names the quarantine and backup trees,
Imunify360/ai-bolit/CloudLinux, maldet/cPGuard/ClamAV/rkhunter and cPanel's
3rdparty — and **omits `node_modules`, `cache`, `.cache` and `virtfs`
entirely**. Adding four entries to a list that already exists costs nothing,
touches no scan path, and turns the biggest known hole in the product from
invisible into disclosed. That I would ship tonight.

### 7. `quarantine restore --signature='*' --apply` defeats the unscoped-restore refusal — blocker (carried forward, still present at `55bd3d5`)

`selector()` refuses a restore with no scope but never checks that the scope is
*narrow*. `--signature='*'` becomes `threat_name LIKE '%'`, matching every
quarantined row in every job for every account under every signature. One
command, no dry run required, restored a `{HEX}php.cmdshell.gifheader` webshell
to `/home/victim/public_html/evil.php` and exited 0. `--ext=md` alone is the
same hole.

`04aefc1` refuses a suppression prefix shorter than eight characters for exactly
this reason. The path that writes attacker code back onto a live docroot has no
such floor.

**Reproduce:**
```
docker compose -f docker/compose.yml run --rm --entrypoint bash shell -lc \
  '/usr/local/bin/entrypoint.sh install >/dev/null 2>&1; bash /opt/serverscrub-src/tests/tools/restore-probe.sh'
```
Section A is refused correctly; section B is not.

```
──────── B. SCOPE BYPASS: --signature='*' with --apply ────────
Restored:        3 file(s), 64 bytes        exit=0
webshell back on disk? YES-BAD
-rw-r--r-- 1 deepnest deepnest 20 Nov 13 20:29 /home/victim/public_html/evil.php
```

I listed this first in the `386bca0` report and am listing it again because
nothing has changed. It is the cheapest blocker here to fix.

## What passed

- **The rework does what the spec asked.** Requirements 1–6 met: no halt; nothing
  in the class writes to `scan_jobs` at all; destructive action still stops past
  the bound; the verdict is computed from sampled `threats.hash` and stated with
  its basis and sample size; "it does not know" is a real answer with its own
  wording; the alarm is still `critical` and immediate, with account spread,
  extensions and both commands. Requirement 7 is the one that failed (blocker 3).
- **The regression test is real.** 44/44 at `55bd3d5`, 13 failures at `386bca0`.
- **The verdict reads 30 Apr correctly.** 154,323 matches of one distinct file →
  `mass-identical`, with "do NOT suppress the signature" in the reason. The
  blind case (no usable hash) → `undetermined` with "No file content hash was
  available", scored as evidence for neither verdict rather than as distinct
  files — which would have read as a false positive.
- **`CLUSTER_FLOOR` and `CLUSTERED_SHARE` fixed the two threshold gaps** I found
  earlier today: `weigh(600, 4, 150)` → `mass-identical` (per-account note),
  `weigh(500, 251, 250)` → `undetermined` (mixed job).
- **Not re-reading files from disk is right** and the docblock's reason is
  correct: at trip time the matches before the bound are already quarantined, so
  a disk read would find exactly those files missing and call every real mass
  event undetermined.
- **PHP 7.4 floor and 8.2 ceiling.** Both images build; parse gate clean at
  7.4.33; **4,660 assertions pass, exit 0, on both streams.** No `match()`, no
  `str_contains`/`str_starts_with`/`str_ends_with`, no `?->`, no attributes in
  `backend/` or `frontend/`. (Wasooli reported 4,656 — the four extra are mine:
  file-iterating tests pick up my untracked `tests/tools/` scripts.)
- **The harness can fail.** Verified, not assumed: a deliberately failing test
  gives `run.php exit: 1`.
- **Upgrade 4.35.1 → candidate.** `PRAGMA integrity_check` → `ok`,
  `foreign_key_check` clean, `waf_exclusions` present, settings canary survived,
  db dir `700`, `db-check` → `ok: yes`, and the new `waf exclude` CLI works
  against the upgraded database.
- **Concurrency.** Scan + scheduler + 25 CLI invocations on one sqlite file: no
  `SQLITE_BUSY`, no locked errors, no WAL growth, `integrity_check` → `ok` after.
- **Scans are bounded and terminate.** Full sweep of `/home` in **4 s** at load
  0.43 with the virtfs tree present; 0 findings under `/home/virtfs`; 1,345 of
  1,645 files read, the gap being the pruned trees. Both walks build the prune
  from the same `SCAN_SKIP_DIRS`, so they cannot disagree again.
- **`quarantine restore`, everything except the scope floor.** `--apply` is the
  only thing that moves a file; a hash mismatch is **FAILED**, not skipped; a
  file that exists again at the original path is **skipped, never overwritten**;
  ownership came back `deepnest:deepnest` inferred from the directory, **not**
  `root:root`; the legacy quarantine directory is searched and a row with no
  `quarantine_path` was found and restored from it; the report is
  restored/skipped/failed with reasons and examples, and names where it looked.
- **Scanner panel empty states.** "No scans have run yet", "No threats found.
  Run a scan to check your server.", "Nothing marked yet.", and "No signatures
  are suppressed. Every signature is reported." as a string distinct from an
  unreadable list. None of them green.
- **Controls respond.** Every Refresh/Reload clicked; threats table shows
  `Updated <time>`; scanner-log refresh answers within a second; all 37
  `api.cgi` calls returned 200.
- **The WAF MODE tile reads `Unknown`**, not `On`.
