## New findings

### N1. `crsVersion()` cannot read the version of a real CRS tree — minor

**What happens:** against the genuine CRS 4.7.0 `crs-setup.conf`, the regex
matches nothing and the function returns `unknown`:

```
=== the product regex against the real file ===
matched: false  captured: NULL
```

**Why:** `/OWASP_CRS.*?ver[^\d\n]*(\d[\d.]*)/i` expects `OWASP_CRS` before
`ver`. The real text is the other way round, on one line:

```
#    ver:'OWASP_CRS/4.7.0',\
```

9c5917e fixed this regex once (it was capturing `.4.7.0`) but the ordering is
still wrong. A tree the product installed itself survives on the `.crs-version`
marker `installCrs()` writes; **any tree it did not install — cPanel's vendor
OWASP3 tree, the distro package, a hand-installed one — reports `unknown`**,
and the panel renders the literal string `vunknown`.

**Expected:** `#OWASP_CRS/(\d[\d.]*)#`, which I verified returns `4.7.0` on the
real file.

### N2. The two subtlest checks in `restoreConfig()` are not covered by any test — major

Mutations M2, M3 and M6 above: delete the short-count (ENOSPC) check or the
byte-readback check and **the entire suite stays green**. These are precisely
the two cases called out in the last report — `file_put_contents` returns a
short count rather than `false` on a full filesystem — and they are the ones a
future edit will quietly remove.

**Expected:** `test_waf_restore_verified.php` gains two cases: a genuine short
write (a small tmpfs is enough) and a readback mismatch. I did not write them
myself because `tests/` changes that pin product behaviour should be reviewed
alongside the fix, and I would rather name the gap than quietly close it.

### N3. `crsPath()` has no override, so the new category feature cannot be tested on a realistic host — major (testability)

All 13 `waf_categories_real` failures have one cause. `crsPath()` tries two
fixed system paths before `confDir()/coreruleset`:

```php
'/etc/apache2/conf.d/modsec_vendor_configs/OWASP3/crs-setup.conf',
'/etc/httpd/modsecurity.d/owasp-crs/crs-setup.conf',
self::confDir() . '/coreruleset/crs-setup.conf',
```

The preference is **correct** on a real server — the vendor tree is the live
one. But `setConfDir()` and `setIncludeDir()` exist precisely so these paths can
be redirected in tests, and `crsPath()` has no equivalent. So the test passes
only on a machine with no system CRS, and fails on every machine that resembles
a cPanel server — which is the only kind that matters.

This is the same shape as finding 10 (`scan_types`), now repeated in new code.

**Expected:** a `setCrsPath()` alongside the other two setters, or the candidate
list made injectable. Then the test asserts against the seeded layout instead of
against its absence.

### N4. `duplicateRuleIds()` cannot see a second CRS that Apache already loads — major

The check inspects the tree it is staging, in isolation. It cannot see a CRS
already included from somewhere else. Installing our CRS 4.7.0 on this image —
which has the distro `mod_security_crs` 3.3.4 at `/etc/httpd/modsecurity.d/`,
loaded by `IncludeOptional modsecurity.d/*.conf` — produced:

```
AH00526: Syntax error on line 818 of /etc/serverscrub/waf/coreruleset/crs-setup.conf:
ModSecurity: Found another rule with the same id
```

Both trees define `id:900990`. Each is individually valid; together they are the
6 Oct failure. **cPanel ships a vendor ruleset, so this is a real configuration
to expect on a customer's server.**

**The layered defence held, and this is worth saying.** `setMode()` ran real
`apachectl -t`, got the rejection, rolled back, and reported
`rolled_back: true, restored_ok: true, restored_validates: true` with the config
correctly absent and Apache valid afterwards. Nothing went live. That is the
design working.

**Expected:** no code change required for safety. But the operator-facing
message for this case could name it — "another ModSecurity ruleset on this
server already defines <id>" is actionable; "Found another rule with the same
id" sends them looking in our tree, which is clean.

### N5. Two test files abort part-way at PHP 7.4, costing ~159 assertions — major (test defect)

```
bruteforce_ladder:      ReflectionException: Cannot access non-public member FirewallEngine::$backend
firewall_rules_paging:  ReflectionException: Trying to invoke private method Database::migrate()
```

PHP 8.1 made `ReflectionMethod::setAccessible()` implicit; 7.4 requires it. Both
files die at the offending line, so **every assertion after it never runs**. The
suite reports 4,115 assertions at 7.4 against 4,274 at 8.2 — a 159-assertion
hole at the floor version, and it presents as two tidy failure lines rather than
as missing coverage.

**Expected:** `->setAccessible(true)` before the access in both files. Mine to
fix if you would rather; I have left them so the count in this report is the one
you can reproduce.

### N6. An auth failure is returned as HTTP 200 — minor

Every unauthenticated route in the sweep answered
`refused (200): Missing authorization token` — `success:false` inside a 200
envelope. A client cannot distinguish "not logged in" from "logged in, nothing
to report" by status code. 401 is the answer.

**And a correction, because I repeated the claim in code comments and in the

the file on disk is truncated and /etc is full, rather than "it could not be
